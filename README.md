# Практична робота №7

## Експерименти з підвищеним навантаженням: оптимізація серверних скриптів

**Варіант 15 — Система бронювання квитків**

### Мета роботи

Виміряти продуктивність PHP-застосунку, провести навантажувальне тестування та застосувати базові методи оптимізації: усунення проблеми N+1, використання індексів бази даних і кешування результатів запитів.

## Використані технології

- PHP
- MySQL
- PDO
- Apache Bench (`ab`)
- файлове кешування

## 3. Проблема N+1

До оптимізації спочатку виконувався один SQL-запит для отримання списку подій.

Після цього для кожної події окремо виконувався запит, який визначав кількість подій у тому самому місці проведення (`venue`).

Для трьох подій виконувалося:

```text
1 запит для списку подій
+
3 окремі COUNT-запити
=
4 SQL-запити
```

Отже, було продемонстровано проблему N+1.

---

## 4. Індекс для venue

Для перевірки роботи запиту було використано:

```sql
EXPLAIN SELECT * FROM events
WHERE venue = 'Stereo Plaza';
```

### До створення індексу

MySQL використовував повне сканування таблиці:

```text
Table scan on events
rows = 3
```

Було створено індекс:

```sql
CREATE INDEX idx_events_venue
ON events (venue);
```

### Після створення індексу

`EXPLAIN` показав:

```text
Index lookup on events using idx_events_venue
rows = 1
```

Отже, для пошуку за `venue` MySQL почав використовувати індекс замість повного сканування таблиці.

---

## 5. Усунення N+1

Замість окремого запиту для кожної події використано один агрегатний запит:

```sql
SELECT venue, COUNT(*) AS event_count
FROM events
GROUP BY venue;
```

Після оптимізації кількість SQL-запитів зменшилася:

```text
До:    4 SQL-запити
Після: 2 SQL-запити
```

При цьому результат API залишився тим самим.

---

## 6. Кешування soldOutList()

Для списку подій без вільних місць реалізовано файловий кеш із TTL **60 секунд**.

Запит:

```text
GET /api.php?resource=events&action=soldout
```

При першому зверненні:

```text
cache: miss
sql_query_count: 1
```

Дані отримуються з MySQL та записуються у файловий кеш.

При повторному зверненні:

```text
cache: hit
sql_query_count: 0
```

У цьому випадку SQL-запит не виконується, а результат береться безпосередньо з кешу.

Після створення нової події або успішної купівлі квитка кеш очищається, щоб користувач не отримував застарілі дані.

Після усунення N+1:

- час виконання PHP: **0.090 ms**
- пікова пам'ять: **2 MB**
- кількість SQL-запитів: **2**

Результат повторного Apache Bench:

- Requests per second: **2426.45 #/sec**
- Time per request: **8.242 ms**
- Time per request across concurrent requests: **0.412 ms**
- Failed requests: **0**

## Порівняння результатів

| Показник | До оптимізації | Після оптимізації |
|---|---:|---:|
| Час виконання PHP | 0.619 ms | 0.090 ms |
| Пікова пам'ять | 2 MB | 2 MB |
| SQL-запити | 4 | 2 |
| Requests per second | 2610.59 | 2426.45 |
| Time per request | 7.661 ms | 8.242 ms |
| Failed requests | 0 | 0 |

Зменшення кількості SQL-запитів з 4 до 2 та використання індексу зменшили обсяг роботи, яку виконує база даних. Час виконання PHP у проведеному вимірюванні зменшився з 0.619 ms до 0.090 ms.

Показники Apache Bench дещо відрізняються між запусками. Після оптимізації Requests per second у конкретному тесті виявився нижчим, однак таблиця містить лише три записи, а тест проводився на локальному вбудованому PHP-сервері, тому невеликі коливання результатів є очікуваними.

## Висновок

У ході практичної роботи було проведено профілювання PHP-застосунку та навантажувальне тестування. Було виявлено проблему N+1, кількість SQL-запитів зменшено з 4 до 2 за допомогою `GROUP BY`, створено індекс для стовпця `venue` та реалізовано файлове кешування списку подій без вільних місць. Також реалізовано інвалідацію кешу після зміни даних.
